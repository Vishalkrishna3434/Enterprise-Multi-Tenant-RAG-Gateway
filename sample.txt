# Enterprise Multi-Tenant RAG Gateway: High-Level Design (HLD) and Low-Level Design (LLD)

## 1. High-Level Design (HLD) Overview
The Enterprise Multi-Tenant RAG Gateway is designed to provide secure, scalable, and isolated document retrieval and generation services across multiple enterprise clients (tenants). The system architecture decouples the ingestion pipeline from the query execution engine, ensuring high availability and low latency. 

At the macro level, incoming documents flow through asynchronous document loaders, undergo hierarchical text splitting, pass through dense embedding models, and are indexed into a multi-tenant vector store. The gateway layer intercepts all user queries, applies tenant-level authorization checks, executes hybrid retrieval (combining dense vector search and sparse BM25 keyword matching), fuses results using Reciprocal Rank Fusion (RRF), and streams responses back via FastAPI endpoints.

## 2. Multi-Tenant Data Isolation Strategy
Data security and isolation are core pillars of the HLD. Tenant data must never cross boundaries during vector similarity searches or metadata filtering. 
- Namespace Separation: Each tenant is assigned a dedicated collection or isolated namespace within the vector database (e.g., Chroma or Qdrant).
- Metadata Filtering: Every chunk indexed in the vector store carries strict metadata tags, including tenant_id, source_document_id, and access_control_lists (ACL).
- Gateway Enforcement: The RAG gateway middleware injects mandatory tenant filters into every query payload before executing database lookups, preventing cross-tenant data leaks.

## 3. Low-Level Design (LLD): Hierarchical Chunking Engine
To resolve the trade-off between granular vector matching and rich context generation, the LLD implements a Parent-Child (Small-to-Big) chunking strategy using LangChain.

- Parent Chunks: Large document blocks (configured with a chunk_size of 1500 characters and a chunk_overlap of 200 characters) are generated to capture comprehensive contextual information required by large language models.
- Child Chunks: Each parent block is sub-divided into granular chunks (configured with a chunk_size of 400 characters and a chunk_overlap of 50 characters). These child chunks are optimized for dense vector embeddings and high-precision similarity matching.
- Metadata Mapping: Child chunks maintain a programmatic link back to their parent block via a unique parent_id stored within the chunk metadata dictionary. During retrieval, the vector database matches the granular child chunk, and the gateway resolves the full parent context block for LLM generation.

## 4. Low-Level Design (LLD): Hybrid Retrieval and RRF
The retrieval component combines dense vector representations with sparse keyword indexing:
- Dense Search: Utilizes SentenceTransformers to map text segments into dense vector spaces, capturing semantic similarity.
- Sparse Search: Utilizes BM25 algorithm models to score exact keyword matches and domain-specific terminology.
- Score Fusion: Results from both retrieval methods are normalized and combined using Reciprocal Rank Fusion (RRF) algorithms to maximize recall and precision before final context assembly.
